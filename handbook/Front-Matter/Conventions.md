# Conventions

## Purpose

This document establishes the editorial, formatting, terminology, and documentation conventions used throughout the Atlas Curriculum Engineering Framework (ACEF).

These conventions promote consistency across all Atlas publications and provide a common set of expectations for authors, reviewers, contributors, and software tools.

Unless otherwise specified, all Atlas publications shall conform to the conventions described in this handbook.

---

# Document Types

Atlas publications are organized into several document categories.

| Type | Purpose |
|-------|---------|
| Handbook | Defines the body of knowledge for Curriculum Engineering. |
| Standard | Establishes mandatory requirements and normative guidance. |
| Specification | Describes how standards are implemented. |
| Template | Provides reusable document structures and examples. |
| Reference Implementation | Demonstrates Atlas applied to real educational systems. |
| Research Paper | Explores new ideas, methodologies, or future enhancements. |

Each document type serves a distinct purpose within the Atlas Framework.

---

# Language

Atlas publications shall be written using American English.

Authors should strive for language that is:

- Clear
- Concise
- Precise
- Professional
- Objective
- Inclusive

Unnecessary jargon should be avoided unless it is defined within the handbook or glossary.

---

# Writing Style

Atlas adopts a technical writing style similar to professional engineering publications.

Authors should:

- Write in the third person whenever practical.
- Use active voice whenever possible.
- Avoid unnecessary repetition.
- Present concepts logically.
- Separate facts from opinions.
- Support claims with references where appropriate.

Example:

**Preferred**

> Curriculum Engineering applies systems thinking to educational systems.

**Avoid**

> We think Curriculum Engineering is probably a better way to build curriculum.

---

# Terminology

Terminology shall remain consistent throughout all Atlas publications.

Key terms defined in the Atlas Glossary shall always use their official definitions.

Examples include:

- Curriculum Engineering
- Educational System
- Learning Outcome
- Educational Artifact
- Knowledge Domain
- Competency
- Atlas Method

Authors should avoid introducing alternate terminology for established Atlas concepts.

---

# Requirement Keywords

Atlas follows the requirement keyword conventions established by RFC 2119 and ISO standards.

| Keyword | Meaning |
|----------|---------|
| SHALL | Mandatory requirement. |
| SHALL NOT | Prohibited action. |
| SHOULD | Strong recommendation. |
| SHOULD NOT | Action generally discouraged. |
| MAY | Optional implementation. |
| CAN | Indicates capability or possibility. |

These keywords are reserved for normative documents such as Atlas Standards and Specifications.

The Atlas Handbook uses explanatory language rather than normative requirements unless explicitly stated.

---

# Capitalization

Official Atlas components shall be capitalized.

Examples:

- Atlas Framework
- Atlas Method
- Atlas Handbook
- Atlas Studio
- Curriculum Engineering
- Reference Implementation

Generic concepts remain lowercase.

Examples:

- educational system
- learning activity
- curriculum artifact
- assessment rubric

---

# Numbers

Numbers from one through nine should generally be written as words unless they represent:

- Measurements
- Percentages
- Versions
- Tables
- Figures
- Technical values

Examples:

- three learning outcomes
- Version 1.0
- Figure 5
- Table 2

---

# Dates

Dates should follow the format:

Month Day, Year

Example:

July 25, 2026

---

# Version Numbers

Atlas publications follow semantic versioning.

Major.Minor.Revision

Examples:

- 1.0.0
- 1.1.0
- 2.0.0

Major versions indicate significant changes.

Minor versions introduce new functionality while maintaining compatibility.

Revision versions correct errors or clarify existing content.

---

# Document Identifiers

Every Atlas publication shall receive a unique document identifier.

Examples:

ATLAS-HBK-001

ATLAS-STD-001

ATLAS-SPEC-003

ATLAS-TMP-002

ATLAS-REF-001

These identifiers support version control, traceability, and document governance.

---

# Chapter Organization

Each handbook chapter should follow a common structure.

1. Chapter Overview
2. Learning Objectives
3. Introduction
4. Core Concepts
5. Engineering Perspective
6. Atlas Perspective
7. Practical Example
8. Summary
9. Key Takeaways
10. Reflection Questions
11. References
12. Looking Ahead

Maintaining a consistent chapter structure improves readability and navigation.

---

# Figures

Figures shall be numbered sequentially within each chapter.

Example:

Figure 3-1

Figure 3-2

Every figure should include:

- Figure number
- Descriptive title
- Caption when necessary

Figures should be referenced within the surrounding text before they appear.

---

# Tables

Tables shall follow the same numbering convention as figures.

Example:

Table 5-1

Table 5-2

Each table should include a descriptive title.

---

# Examples

Examples illustrate practical application of concepts.

Example callouts should be clearly identified.

> **Example**
>
> Developing a Course Learning Outcome Matrix for a software development course.

Examples are informative and do not establish requirements.

---

# Notes

Notes provide additional explanatory information.

> **Note**
>
> Atlas Standards define implementation requirements. The handbook explains the underlying concepts.

Notes are informative only.

---

# Engineering Insights

Engineering Insights highlight the engineering rationale behind a concept.

> **Engineering Insight**
>
> Traceability enables educators to determine how every learning activity supports one or more program outcomes.

These callouts emphasize the engineering perspective unique to Atlas.

---

# References

Whenever possible, references should cite authoritative sources, including:

- Peer-reviewed journals
- Engineering standards
- Accreditation guidance
- Government publications
- Academic books
- Industry publications

References should be complete and consistently formatted.

---

# Cross References

Internal references should use official chapter numbers and section titles.

Example:

See Chapter 6, *The Atlas Method*, for additional discussion.

Avoid vague references such as "earlier in this book."

---

# Continuous Improvement

Atlas publications are living documents.

Corrections, clarifications, and enhancements should be documented through the established governance and version control processes.

Each published edition should include a documented revision history.

---

# Guiding Principle

Consistency is a hallmark of every mature engineering discipline.

These conventions establish a common language and structure for the Atlas Curriculum Engineering Framework, ensuring that every publication contributes to a coherent, professional, and evolving body of knowledge.
